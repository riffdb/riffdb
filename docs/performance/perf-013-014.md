# PERF-013 / PERF-014 — linear startup and unclean recovery

Proposed gates (ADR-0073), **off by default** until drain-inclusive measurements
are stable on CI hardware:

- **PERF-013**: `t_startup(65536) / t_startup(4096) <= 32` AND
  `t_startup(65536) <= 30s`, where `startup` is the full structural + historical
  evidence drain plus operational handoff (not merely `RedbStore::open`).
- **PERF-014**: unclean recovery wall time ≤ 3× clean startup at each checked
  checkpoint, where unclean recovery opens a file that exercised redb repair
  (kill-without-close of a writer process).

Enable with `--assert-perf-013` on `benchmarks/command-growth` after recording
fresh JSONL evidence.

## PERF-014 status (RT-A)

Real unclean recovery evidence is exercised by
`tests/storage_recovery/storage_recovery_matrix.rs::perf_014_unclean_recovery_vs_clean_startup`:

1. Seed TWO databases identically (initialization + catalog activation): the
   comparison is between equivalent committed states — the aborted write below
   is invisible to committed state by engine atomicity.
2. Kill the unclean copy mid-`CommandBatch` via the existing
   `before-command-batch-commit` child failpoint (`run_crashing_child`).
3. Reset the process-global repair observation to a sentinel, reopen the
   unclean file, and **assert** `last_repair_progress_basis_points()` changed —
   the redb repair callback provably fired for this open (0% progress is
   distinguishable from never-fired). The observable remains process-global, so
   attribution is exact only when no parallel test triggers a repair between
   the reset and the open.
4. Full structural/historical drain on both; compare wall times.
5. Emit one JSON evidence line. Measured on the development workstation
   (Samsung 990 PRO, ext4):
   `{"schema":"riffdb.perf-014/v1","repair_progress_bps":9000,"unclean_ns":10794294,"clean_ns":7741404,"ratio":1.39}`.

**Gate policy:** do **not** reintroduce a hard PERF-014 ratio ≤3× assert until the
ratio is stable on CI hardware. The test reports the measured ratio honestly and
does not fail on ratio alone. (The measured 1.39× at the small fixture size is
within the proposed ≤3× envelope but is not yet CI-validated at the checked
checkpoints.)

Validated-prefix startup checkpoints (ADR-0085 Amendment 1) reduce clean startup
cost for large histories; unclean recovery still pays redb repair + full or
suffix validation. Measure checkpointed clean reopen with
`benchmarks/command-growth --startup-scale N --startup-scale-checkpointed`
(`record_type: startup_scale_checkpointed`). The record's `checkpoint_verified`
and `suffix_commands` fields derive from the validation session's own
observability, never from the CLI flag, and a plain `--startup-scale` baseline
strips any stored checkpoint (bench-only raw-transaction affordance) before
measuring so a reused database always yields an honest full-validation curve.

## Clean-lifecycle stage evidence

Production lifecycle evidence separates costs that earlier reports combined:

- `store_open` is engine open;
- `evidence_begin` is the bounded-root and lifecycle eligibility decision;
- `structural_drain` plus `catalog_history` is complete validation when dirty;
- `evidence_finish` includes clean-certificate consumption before activation;
- `process_to_ready` is complete daemon readiness;
- the eight shutdown stages retain drain and the legacy-labelled bounded
  checkpoint-close stage;
- `riffdb-graceful-checkpoint-close-v1` separately records the journal barrier,
  the closed retained-checkpoint disposition and classification time, and the
  final clean-certificate commit status/time. Graceful close does not create or
  refresh a validated-prefix checkpoint.

The fixed-cardinality observations do not turn a duration into a deadline and
cannot be supplied as control input. Clean production-scale evidence must also
observe the clean mode and no population-table walk. Dirty kill/reopen evidence
must report complete validation and real engine repair/recovery separately; it
is not relabelled as a clean measurement. PostgreSQL is excluded from this
lifecycle comparison because the harness does not own an equivalent server
process, integrity validation path, and final certificate ceremony.

On Linux, each clean-lifecycle memory sample binds one `riffdbd` PID to field
22 (`starttime`) from `/proc/<pid>/stat`, so PID reuse or sampling a launcher
invalidates the report. The initial sample is synchronized to a fixed internal
post-exec marker emitted after runtime and signal setup but before any database
open, so it cannot race the child across `fork`/`exec` or subtract a launcher
image. `heap_envelope_bytes` is the positive `VmData` change over the named
lifecycle window and must be at most 64 MiB. `VmHWM` remains a separate
peak-resident diagnostic; it cannot substitute for `VmData`. The
canonical-production heap envelope may be at most 16 MiB above the exact
65,536-entity checkpoint. Both checkpoints must report all closed startup and
shutdown stages and exactly zero rows for the complete prohibited population-
table registry.

The 65,536-row dirty complete-validation arm records the same PID-bound memory
fields but makes no WP-705 heap claim: its ceiling and pass fields are absent
and `gate_owner` names WP-760. WP-760 alone owns the production dirty-recovery
64 MiB gate. This does not relax WP-705's 64 MiB gates for clean restart or
clean shutdown.

The production redb adapter fixes its internal page-cache budget at 4 MiB and
dedicated post-baseline worker stacks at 384 KiB. The blocking-port worker set
is eight threads. Together those fixed reservations keep graph construction
inside the 64 MiB lifecycle envelope instead of inheriting redb's
population-sensitive 1 GiB default or platform-default thread stacks.

Qualification builds its own default-feature production daemon with
`cargo +1.97.0 build --locked --release`; the 65,536-row SIGKILL arm separately
identifies its `test-fixtures` binary. The retained reports close the source
revision, lockfile, runner, daemon, harness, referee, and raw-report digests,
and `scripts/wp705-lifecycle-referee` rejects any missing or mismatched member.
This is not the WP-760 dirty-recovery memory proof and is not the pending
WP-578 72-hour receipt.

At the canonical production population, the unchanged dirty complete path has
one retained fail-closed `LimitExceeded` receipt at the 512 MiB
historical-evidence ceiling. It is a handoff rather than a passing PERF-014 or
readiness result and must not be retried by raising the ceiling.
