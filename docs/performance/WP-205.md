# WP-205 application-path performance

## Work-package contract

Work package:
WP-205, Application-path latency decomposition and optimization baseline

Requirement IDs:
PERF-001, PERF-002

ADRs consulted:
ADR-0007, ADR-0009, ADR-0025, ADR-0026, ADR-0027, ADR-0053

Upstream revision:
`82d76d2` (WP-200/TicketDesk baseline), with the v0.36 architecture checkpoint
at `3e72ac6`

Allowed paths used:
`crates/riffdb-server/**`, `scripts/benchmark-application-path`,
`benchmarks/application-path/**`, and `docs/performance/**`

Behavior added or changed:
Accepted gRPC connections set `TCP_NODELAY`; immutable process-local capability
and exact historical-contract views avoid repeated decode/storage work and
publish capability revisions under the same synchronization boundary as
capability commit.

Compatibility classification:
Compatible implementation optimization. The `riffdb.v1` wire, durable records,
command semantics, authorization safe points, and response shapes are unchanged.

Security implications:
Authentication still computes digest candidates for every RPC. Every existing
authorization safe point still resolves current capability state and samples
its clock. Capability create/bootstrap/revoke holds the view publication lock
across authoritative commit and publication, so a later safe point cannot
observe an older published revision. Cache poison, identity conflict, or
capacity exhaustion fails closed.

Generated artifacts checked:
The benchmark report is produced deterministically from the existing bounded
TicketDesk JSON report. No protocol or durable generated artifact changes.

Known limitations:
Command p50 and the sequential 276-row seed remain above `PERF-002`; this is a
measured WP-205 blocker, not a waived gate. WP-270 must use bounded concurrent
ordinary commands, and command-path work must reduce its three serial durable
transitions without weakening audit or command atomicity.

Follow-up issues:
Complete the startup full-view rebuild/readiness proof, add closed per-stage
histograms, and optimize command/audit batching under the accepted durability
semantics.

## Reproduced baseline

The initial smoke run used one live `riffdbd`, one reused HTTP/2 client channel,
276 authoritative seed rows, three measured samples, and one warmup.

| Scenario | Before p50 |
|---|---:|
| Point ticket | 46.553 ms |
| Point user | 43.293 ms |
| Project/status list | 226.909 ms |
| Assignee list | 140.030 ms |
| Comments list | 223.341 ms |
| Project members | 173.607 ms |
| Ticket detail | 493.493 ms |
| Create comment | 76.462 ms |
| Seed | 17.246 s |

The syscall profile showed 2,252 `fdatasync` calls across bootstrap, seed, and
scenarios, but their accumulated syscall time was under one millisecond. The
fixed read latency instead matched the Linux delayed-ACK interval. Tonic's
client endpoint already enables `TCP_NODELAY`; the accepted server sockets did
not.

## Result after disabling Nagle on accepted gRPC sockets

The first three-sample verification after the fix measured:

| Scenario | After p50 | Change |
|---|---:|---:|
| Point ticket | 0.212 ms | 99.5% lower |
| Point user | 0.173 ms | 99.6% lower |
| Project/status list | 0.715 ms | 99.7% lower |
| Assignee list | 0.411 ms | 99.7% lower |
| Comments list | 0.618 ms | 99.7% lower |
| Project members | 0.481 ms | 99.7% lower |
| Ticket detail | 1.350 ms | 99.7% lower |
| Create comment | 31.532 ms | 58.8% lower |
| Seed | 4.810 s | 72.1% lower |

The complete fastest point request is below 0.2 ms, so it also places a strict
upper bound below the 1 ms unary transport/adaptation gate. This is sufficient
to retain unary gRPC: replacing the protocol cannot improve transport by more
than the complete request currently costs.

Reads pass the current `PERF-002` point/list/detail gates even though the
TicketDesk baseline still performs public N+1 calls. WP-240 remains necessary
for one-snapshot semantics, stable query shapes, and scale behavior—not to
repair transport overhead.

The remaining command time is structurally different: a mutation durably
records its audit start, authoritative command graph, and terminal audit in
three ordered transitions. Sequential seeding repeats that lifecycle 276 times.
Those are the next optimization targets; neither can be skipped or made
memory-only to satisfy a benchmark.

## Reproduction

Run:

```bash
./scripts/benchmark-application-path --assert-wp205
```

The script builds locked release binaries, runs nine samples after two warmups,
writes `benchmarks/application-path/latest-v1.json`, and enforces the WP-205
read and unary bounds. It deliberately records rather than waives the remaining
command and seed gates.
