# WP-825: explicit catalog fencing compatibility review

Status: accepted by the maintainer in session on 2026-10-16:
"Accept ADR-0325 and its SPEC/WP-825 amendments as written".
Catalog V3 activation and successor fencing implementation remain pending.

The existing primary-admission and fence V1 records omit catalog identity.
Their constructors and decoders reconstruct catalog V2. Promotion V1 embeds
that fence. Accepting V3 by widening runtime checks would either lose the
exact lineage or bypass current source fencing. This is a database compatibility
blocker, independent of the campaign harness.

Review the exact [ADR-0325](../../adr/0325-explicit-catalog-binding-for-primary-fencing-and-promotion.md),
the [SPEC](../../SPEC.md) and [WP-825 registration](../../work_packages.yaml).
Acceptance applies to the final reviewed text, including the clarification that
attached bootstrap transfers no source-only admission state.

The decision adds three revision-2 durable records with explicit catalog
binding while preserving revision-1 bytes and V2 meaning. V3 inherits current
authorization, atomic fencing, authenticated promotion, startup point checks,
scrub authority withdrawal and exact retry/recovery rules. There is no unfence.
Offline upgrade accepts only validated Active V2 predecessors with complete
authoritative plan input; Fenced or unresolved predecessors refuse this upgrade.

Follower configuration gains only optional `catalog_version = 2|3`; absence
continues to mean 2. Helm has the matching optional `catalogVersion`. Selection
cannot override exact persisted lineage, authenticated source, configured hold,
validated registration or current administrative authority. Existing payload,
resource and recovery limits remain unchanged.

WP-825's accepted registration adds REP-002/003/005/007 proof ownership, ADR-0325,
its record path and `release/helm/**`. Existing source, API, server, commit,
fixture, script and documentation paths are already in scope. Closure remains
open. New schema hashes, bounds, wire vectors and inventory diffs still need
their own concrete fixture review; accepting this decision does not accept
unseen generated bytes.

The audit identifies the integration areas together:

| Area | Required work before activation |
| --- | --- |
| Durable admission/fence/promotion | Add exact successors and mixed-version validation |
| Promotion and incarnation transitions | Preserve authenticated evidence; attribute source allocator reset |
| Startup/readiness/scrub | Extend existing checks and authority withdrawal to V3 |
| Restore | Preserve inherited source identity and fenced-source restrictions |
| Physical/state inventory | Select exact catalog; keep generation bases derived and local |
| Offline upgrade | Prove Active predecessor and complete source closure; refuse otherwise |
| Bootstrap/archive | Transfer exact authoritative source domains under the captured catalog |
| Follower configuration/peer | Bind closed configuration to checked local state and authenticated source |
