# ADR-0176: Compiler-Bounded Large Atomic Command Envelope

- **Status:** Accepted
- **Direction approved:** 2026-09-01
- **Exact text accepted:** 2026-09-01
- **Acceptance reference:** Maintainer approval in the current Codex session
- **Requires:** ADR-0002, ADR-0003, ADR-0005, ADR-0006, ADR-0007,
  ADR-0008, ADR-0011, ADR-0013, ADR-0031, ADR-0055, ADR-0058,
  ADR-0059, ADR-0124, ADR-0129, ADR-0137, ADR-0147, and ADR-0148
- **Amends:** ADR-0147 only where it retains the 1 MiB complete public
  request envelope for every atomic command
- **Defines or blocks:** WP-744
- **Decision deadline:** Before changing public command framing, canonical
  command-input encoding, command IR, plan hashes, or generated runtimes

The maintainer accepted the direction and authorized its complete end-to-end
implementation on 2026-09-01. The exact numeric limits and least-sufficient
identity rule below are part of the accepted boundary.

## Context

MLflow permits one Run to be created atomically with as many as 100 tags whose
values may each contain 8,000 characters. RiffDB must retain the tags both as
indexed child rows for server-side search and in a bounded packed hydration
field. The complete legal input is therefore approximately 1.8 MiB even though
each individual string, bytes value, list element, entity record, mutation,
and aggregate collection remains within its existing bound.

ADR-0147 correctly introduced a compiler-owned aggregate element-byte budget
and retained the 16 MiB complete canonical input-and-write graph ceiling. It
also retained the original 1 MiB whole-request envelope. That outer envelope
now rejects a compiler-proved safe atomic graph before execution. Splitting the
Run and tag writes would change application atomicity, while omitting indexed
rows or packed hydration would change query or read semantics.

The limitation is generic. An atomic command may combine several independently
bounded values or representations while every authoritative effect remains
within the existing graph, mutation, index, partition, and durability limits.
The solution must bound that combination explicitly without raising ordinary
value, entity, request, response, or graph limits and without allowing callers
or configuration to negotiate resource ceilings.

## Decision

### 1. Add one fixed atomic-command input envelope

The maximum decoded and canonical root input for one atomic command is
4,194,304 bytes (4 MiB). This is a fixed first-party POC ceiling. It is not a
contract literal, configuration option, transport negotiation, role grant, or
caller-selected budget.

Only the complete root command-input record receives this envelope. The
existing 1,048,576-byte canonical document ceiling remains unchanged for every
individual string, bytes value, list, nested record, entity record, event
record, outcome record, query/service request, and other canonical value.
Cardinality, nesting, mutation, index-work, partition, diagnostic, response,
and retry ceilings remain independent and unchanged.

The existing 16 MiB complete canonical input-and-write graph ceiling remains
unchanged. A command must satisfy both the 4 MiB request envelope and every
existing graph/effect proof; neither ceiling grants headroom under the other.

### 2. Make eligibility compiler-proved and least-sufficient

The compiler computes a conservative maximum complete command request from the
closed input schema and any ADR-0147 aggregate correlation. Checked arithmetic
must prove the maximum is at most 4 MiB. A command whose maximum is at most the
legacy 1 MiB retains its exact existing grammar, executable-IR, bundle, plan,
lock, role, and generated bytes.

A command whose proven maximum is greater than 1 MiB and at most 4 MiB selects
contract grammar, executable IR, and bundle V22. Executable IR V22 carries the
compiler-proved maximum request bytes and includes it in command-plan identity.
Decoding recomputes the proof and rejects a substituted or inconsistent bound.
Old readers reject V22 before deployment rather than reinterpreting it.

No new source syntax is required: the capability follows from existing typed
field bounds and the explicit ADR-0147 aggregate constraint. Compilation above
4 MiB fails with the existing safe source-spanned resource diagnostic. A caller
cannot opt a smaller command into V22 or raise a plan's maximum.

### 3. Preserve canonical and idempotency bytes

The ADR-0011 value encoding and field ordering do not change. A command input
that fits the legacy envelope produces byte-for-byte the same canonical bytes
and therefore the same canonical input hash. The command-input encoder changes
only its fixed root document ceiling; nested values retain their prior limits.

Idempotency preparation hashes the complete canonical command input once under
the command envelope. The resulting hash remains part of the same stored
pending/outcome identity. Retry, duplicate submission, outcome recovery, and
post-commit replay reuse the identical input and never split or truncate it.
No command input bytes are newly persisted in commit, provenance, audit, or
diagnostic records.

### 4. Bound public and local framing separately

One complete command-bearing gRPC, application-session, contextual-reaction,
MCP, CLI JSON, command-batch item, or local-driver frame may contain at most
8,388,608 bytes (8 MiB). This fixed framing ceiling provides bounded Protobuf,
JSON field-name, and base64 overhead for a decoded 4 MiB command input; it does
not raise the decoded service or plan ceiling.

Non-command services retain their 1 MiB decoded request ceiling and 4 MiB
response ceiling. Individual base64 bytes values still decode to at most their
ordinary 1 MiB component/document limits. Compression remains disabled. All
Rust, Go, TypeScript, and Python/local paths use the same framing constants and
fail before unbounded allocation or transport work.

### 5. Enforce the exact plan before effects

Transport preflight enforces framing and structural value limits. The shared
service charges a command request against the fixed 4 MiB envelope, resolves
the exact active/historical command plan, materializes the canonical input, and
requires its encoded length to be no greater than that plan's compiler-proved
maximum. This occurs before deterministic evaluation, conflict acquisition,
staging, journaling, or any authoritative effect.

The deterministic runtime retains all existing collection, graph, mutation,
index, partition, and output validation. A valid V22 input either commits its
complete graph and durable outcome atomically or follows the existing typed
pre-commit failure/uncertainty rules. No layer may page, split, stream, omit,
deduplicate, compress, or partially apply command input to fit a limit.

### 6. Keep generated interfaces safe

Generated Rust, Go, TypeScript, and Python command methods continue to expose
only typed values and compiler-owned count/aggregate constraints. Their shared
runtime accepts the 8 MiB frame while retaining individual 1 MiB value checks.
MCP schemas continue to publish exact field, count, and aggregate element-byte
constraints; the plan-specific complete request maximum remains authoritative
service metadata rather than a caller control.

Applications cannot choose envelope version, encoder, frame, command maximum,
transaction boundary, split policy, or fallback. A command not requiring V22
does not silently acquire its larger decoded budget: the exact compiled plan
maximum is rechecked after materialization.

## Options Considered

1. **Raise every public request/value limit:** Rejected because it expands
   unrelated attack and allocation surfaces and weakens existing contracts.
2. **Split Run and tag creation:** Rejected because it violates atomicity and
   changes idempotency, recovery, and observable intermediate state.
3. **Store only packed or only indexed tags:** Rejected because it breaks
   hydration or correct server-side search.
4. **Compress or reference large values:** Rejected because size semantics
   would become representation-dependent and recovery would require external
   state or nondeterministic I/O.
5. **Make the limit configurable or source-selected:** Rejected because an
   application caller/operator could enlarge a resource guarantee without a
   new reviewed runtime identity.
6. **Raise the 16 MiB graph ceiling:** Rejected because the proven command fits
   it and changing durable/effect capacity is unnecessary.

## Consequences

- MLflow can atomically create a Run with all legal tags, indexed children, and
  packed hydration without adapter filtering, splitting, or reduced limits.
- The canonical codec gains one purpose-specific root encoder, the command plan
  gains a maximum-request proof, and public/local command transports reserve
  bounded framing headroom.
- Command-bearing service endpoints can allocate up to 8 MiB of transport
  framing and materialize up to 4 MiB of decoded input. Existing admission,
  concurrency, and graph bounds prevent this from becoming unbounded retained
  state.
- Existing commands stay byte-exact; only commands that need the capability
  require V22 deployment and regenerated exact artifacts.

## Compatibility

The change is source-additive and uses least-sufficient V22 identities. V1
through V21 bundles, plan hashes, locks, roles, generated bindings, canonical
input bytes, idempotency hashes, durable outcomes, entity/index keys, events,
commit records, provenance, and storage formats remain exact. No data migration
or decoder retirement is authorized.

The public Protobuf message schema and driver protocol identity do not change;
their fixed size policy increases only for command-bearing frames. Peers that
retain the old frame ceiling fail safely before submission. A V22 contract must
be recompiled, deployed, rebound, and regenerated as one exact application
identity.

## Security

Every byte limit is fixed, checked with overflow-safe arithmetic, and enforced
before proportional allocation at its owning boundary. Nested values retain
the legacy limit. Compiler proof and service recomputation prevent a transport
frame from granting plan capacity. Authorization, policy, audit, provenance,
redaction, and commit atomicity are unchanged; command values never enter safe
errors, logs, metrics, evidence receipts, or MCP diagnostics.

## Standing Design Tests

- **Interface safety:** applications submit only generated typed command
  values. They cannot select a limit, IR version, frame size, encoder, split,
  transaction, or fallback. The compiler and shared service own all size and
  effect proofs.
- **Scale:** root input, every nested value, aggregate elements, graph bytes,
  mutations, index work, partitions, transport frames, concurrency, retries,
  responses, and diagnostics remain independently finite. The 4 MiB/8 MiB
  limits are reversible POC ceilings, not a claim that larger atomic graphs are
  unbounded or supported.

## Testing

- Exact and plus-one codec, submitted-value, service-request, plan, bundle V22,
  old-byte, and transport-frame boundaries.
- Compiler tests for legacy least-sufficient output, V22 selection, decoded
  proof recomputation, and source-spanned refusal above 4 MiB.
- Service/runtime/idempotency tests proving plan-bound rejection before effects,
  identical legacy hashes, large-input hashing, replay, and no partial graph.
- Rust, Go, TypeScript, Python, gRPC, MCP, CLI, local-driver, generation,
  application-boundary, and downstream-adapter parity.
- Real redb loopback creating one Run with 100 maximum-size legal tags plus
  packed hydration, exact replay, indexed search, hydration, revision, audit,
  provenance, and atomic complete-or-absent visibility.

## Decision Deadline

This exact boundary was accepted before merge. Any increase above the fixed
4 MiB decoded/canonical command input, 8 MiB command frame, or 16 MiB graph;
any widening of individual values or non-command requests; any configurable or
caller-selected budget; or any change to transaction, durable, or uncertainty
semantics requires renewed human review.
